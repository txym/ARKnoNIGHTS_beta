# UI-001：本地玩家状态、真实单位 UI 数据与有序待部署快照

## 角色

你是本 Unity 项目的玩家状态与本地数据接入 Agent。

你的职责是建立当前 UI 接入阶段唯一的玩家状态事实来源，使 Cost、玩家拥有的单位、区域、部署坐标、精英化等级、Buff、严格堆叠和待部署顺序都能在不依赖场景 GameObject 的情况下加载、查询、修改和测试。

本任务只建立数据和领域状态，不制作正式 HUD、不修改 SampleScene，也不接入战斗演示。

## 任务背景

当前 `PlayerUnitCollection` 只是未接入的粗糙原型：它有固定容量 48、四个区域桶和 `9×4` 网格，但没有玩家 Cost、精英化、Buff、严格堆叠、Player-safe 加载、状态变化通知或部署/撤退命令。其公开部署坐标当前为零基，而 SPEC 的游戏规则坐标是一基。

旧 `UnitFactory.SpawnAll` 会扫描 `Application.dataPath/GameData/Units/Json`，为每个类型创建一个临时 GameObject，并使用负数临时 ID。该行为不代表玩家拥有的单位，也不能在 Windows Player 中作为正式自动加载入口。

已有 `unit-catalog-v1` 是 Player-safe 的真实战斗类型目录，但当前只覆盖战斗和表现字段，尚未携带部署 Cost、头像、稀有度和初始精英化等级。当前 UI 不能因此退回到 Player 中读取 Assets 源目录，也不能让 `UnitTemplate` 或场景对象成为第二份权威数据。

## 本任务目标

1. 在真实单位 JSON 中增加明确的初始精英化等级字段，并验证范围。
2. 把 UI 所需的部署 Cost、头像资源、稀有度和初始精英化等级纳入 Player-safe 真实类型目录或等价的唯一运行时类型目录。
3. 建立本地 `PlayerState` 或等价聚合，初始可用部署费用为 `99`，并持有一个 `PlayerUnitCollection`。
4. 扩展玩家单位实例数据，使每个单位包含独立 ID、type ID、区域、精英化等级、Buff 快照和可选的一基本地阵型坐标。
5. 提供只读、不可由 UI 直接篡改的玩家快照和区域查询。
6. 提供严格堆叠后的待部署槽快照，按 Cost 升序、type ID 升序稳定排列。
7. 提供后续 UI-003/004 可调用的原子状态操作：部署到空格、立即撤退、移除 Overflow；失败不改变任何玩家状态或费用。
8. 建立一份 Player-safe 的本地玩家测试状态，使用真实 `gopro`/`arcslma` type ID 和真实资源，不使用合成头像或合成战斗类型。
9. 为加载、验证、排序、容量、费用、区域转换和失败原子性建立轻量 EditMode 测试。
10. 更新受本任务实际改变影响的 ARCHITECTURE、TEST_PLAN 和必要的 SPEC 细节；不得把未执行验证写成已通过。

## 已确认规则

- 玩家状态生命周期贯穿整局游戏；准备/战斗阶段切换不重建玩家单位集合，也不把 Cost 重置为 99。
- 本地测试玩家初始可用部署费用为 `99`。
- 部署成功扣除单位部署 Cost；撤退成功返还 `100%` 已占用部署费用。
- 赤金与部署费用是不同资源；本任务不增加赤金数值。
- 每个单位实例有独立单位 ID、type ID、区域、精英化等级和 Buff。
- 单位 JSON 保存创建实例时使用的初始精英化等级；实例创建后由玩家状态维护当前精英化等级。
- 单位堆叠只存在于待部署区。
- 严格堆叠至少要求 type ID、精英化等级和完整 Buff 状态一致。
- 待部署区最大为 13 个堆叠槽；不可堆叠单位各占一个槽。
- 槽位从左到右按部署 Cost 升序，再按 type ID 升序。
- 部署区和商店不进行待部署区堆叠。
- 玩家本地阵型使用一基 `9×4` 坐标；蓝门 `(5,1)` 不可部署，同一格不能有两个已部署单位。
- Overflow 是玩家单位区域；进入战斗阶段时由阶段状态机调用清理，本任务只提供明确操作。
- 当前战斗死亡、HP 和胜负不写回玩家状态。

## 实施要求

### A. 先确认真实状态与数据契约

1. 检查 `PlayerUnitCollection` 的所有调用方和测试。若没有调用方，也不得直接在同名方法上静默把零基参数解释为一基；选择新增明确的一基 API，或进行有迁移证据的签名调整。
2. 检查 `unit-catalog-v1` 的生成器、加载器、摘要、测试和 Player 验收入口。新增字段必须从真实 `UnitJson` 生成，不能手工维护两份互相漂移的目录。
3. 在修改 `1000_gopro.json`、`5503_arcslma.json` 和 `5504_arcslmi.json` 前确认它们各自的初始精英化等级。不得使用 `Rarity` 推断精英化，不得把临时猜值描述为规则。
4. 类型目录的新增 UI 字段至少应表达：部署 Cost、头像 Resources 路径或可稳定解析的头像名、稀有度、初始精英化等级。可选择加法扩展 `unit-catalog-v1`，但必须保持旧文件缺少新字段时的错误/兼容策略清晰，并更新生成器与加载测试。

### B. 建立玩家状态聚合

5. 建立一个明确拥有当前可用部署费用和玩家单位集合的聚合。不要让多个 MonoBehaviour 各自保存一份 Cost。
6. 玩家状态核心应为普通 C#，不能依赖 MonoBehaviour `Update`、Transform、Unity Physics 或实际渲染帧。
7. 单位实例记录至少包含：稳定 unit ID、type ID、区域、当前精英化等级、不可由外部修改的 Buff 快照、可选的一基本地阵型坐标。
8. 对外暴露只读快照或只读枚举，不暴露内部可变数组、List 或字典。
9. 状态成功改变时提供最小变化通知或版本号，供 UI 重建；失败操作不能发送“成功变化”通知。
10. 保留 `Staging`、`Deployed`、`Overflow`、`Shop` 四种玩家区域。战斗 Core 不需要因此增加 Overflow 区域：后续 BattleInput 适配只选择/转换战斗需要的数据。

### C. 严格堆叠与有序槽位

11. 从玩家单位状态生成待部署“堆叠槽快照”，每个槽包含 type ID、Cost、精英化、Buff 标识、成员 unit ID 和数量。
12. 成员 unit ID 顺序必须稳定，不能依赖 Dictionary 枚举顺序。槽位数量为 1 时也必须保留数量 1，供 UI 显示 `X1`。
13. 第一排序键为部署 Cost 升序，第二排序键为 type ID 升序。
14. 同 Cost、同 type ID 但因精英化/Buff 不同而无法合并的最终决胜尚未确认。把该决胜隔离在明确比较器中；固定测试数据不要依赖它。不得把不稳定对象哈希或集合插入顺序写成长期规则。
15. 对 Buff 快照做完整保留。若当前实现需要比较非空 Buff，而现有文档无法确定等价规则，停止询问；当前本地玩家固定数据可以使用空 Buff 推进。
16. 容量检查按堆叠槽数量而不是单位实例数量执行。所有预计结果先验证，成功后一次性提交，失败时状态完全不变。

### D. 原子状态操作

17. 提供“从待部署区取一个具体单位部署到空格”的原子操作：检查单位/区域、目录类型、Cost、一基边界、门格、占位和结果容量；成功后扣费、改变区域并保存坐标。
18. 从一个堆叠部署时，具体实例选择必须稳定；可使用槽快照中稳定排序的第一个 unit ID。该选择是实例管理细节，不得改变槽排序规则。
19. 提供“部署区单位立即撤退”的原子操作：检查返回后是否能合并或仍有空槽；成功后清除坐标、进入 Staging 并返还 100% Cost；失败保持状态和费用不变。
20. 本任务的部署操作只接受空目标格。发现已占用格时返回明确结果码，不实现替换或交换。
21. 提供“永久移除全部 Overflow 单位”的明确操作，返回被移除的 unit ID 或数量，便于阶段状态机和日志核对。该操作不能被普通 UI 刷新隐式调用。
22. 所有失败使用结构化结果码/诊断，不依赖日志文本作为程序判断依据。

### E. Player-safe 本地玩家测试状态

23. 定义一份简单、版本化、Player-safe 的本地玩家状态输入。字段至少覆盖 schema、player ID、当前 Cost、单位 ID、type ID、区域、精英化、Buff 和部署坐标。
24. 固定数据使用真实 `1000/gopro` 与 `5503/arcslma`，包含：至少两个能够严格堆叠的实例、两个不同 Cost 的类型、至少一个 Overflow 实例、初始部署区为空、非空 Buff 不作为当前测试前置。
25. 固定数据不得出现相同最高可支付 Cost 的自动部署歧义；UI-004 将用它验证最高费用单位自动部署到 `(5,2)`。
26. 加载器拒绝未知 schema、重复 unit ID、未知 type ID、非法区域、非法精英化、负 Cost、区域与坐标不一致、超出固定容量和超过 13 个无法堆叠槽的输入，并返回结构化错误。
27. 不在运行时写回 JSON；加载完成后玩家状态在内存中持续存在。

### F. 收尾

28. 不删除旧 `UnitFactory.SpawnAll`、`UnitTemplate` 或 `PlayerUnitCollection` 公共入口。若旧入口不再用于正式自动加载，保留并在文档中标明 legacy/debug。
29. 审查生成的 `unit-catalog-v1` diff，确保旧战斗字段和真实资源路径没有意外改变。
30. 更新文档只描述实际实现；未运行 Player 加载时必须标记未验证。
