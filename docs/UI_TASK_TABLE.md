# UI 接入阶段任务规划

## 1. 文档用途

本文档记录当前正式 HUD 基线之后的 UI 增量规划，重点覆盖：

- 右上角玩家等级按钮；
- 准备按钮与准备状态；
- 本地确定性商店状态和商店界面；
- 左侧玩家列表；
- 观察其他玩家的场地与待部署区；
- 与现有单位信息面板、部署交互和准备—战斗循环的集成；
- 截图驱动的最终视觉拟合。

历史 `UI-001`～`UI-005`、`PREP-DEPLOY-001`、`UI-INFO-001` 和 `UI-INFO-002` 不重新实施。新任务从 `UI-006` 开始，继续使用独立于战斗 `TASK-XXX` 的 UI 编号。

本文档是任务规划，不代表功能已经实现或验证。游戏规则以 `docs/SPEC.md` 为准，视觉规则以 `docs/references/ui/battle_hud/UI_SPEC.md` 为准，真实架构和验证口径分别以 `docs/ARCHITECTURE.md`、`docs/TEST_PLAN.md` 为准。

## 2. 当前真实基线

### 2.1 已存在且应复用

- `SampleScene` 是当前正式场景入口。
- `PlayerState` 是本地玩家单位、区域、阵型坐标、精英化、Buff 和部署费用的权威来源。
- `StagingHudController` 已能自动加载本地玩家状态并投影有序待部署槽。
- `StateDrivenDeploymentController` 已能部署、撤退和移动/交换已部署单位，并通过 `SetInteractionEnabled` 统一锁定当前部署交互。
- `PreparationBattleLoopController` 已实现 `Preparation(30 秒) → Battle → Preparation`。
- `PreparationBattleSealer` 已能从本地玩家和临时对手的 `PlayerState` 生成不可变战斗输入。
- `BattleDemoController`、`BattleDemoCoordinator` 和事件回放已经可以消费运行时战斗输入。
- `FormalBattleHudUi005` 已建立资源区、顶部状态栏、设置按钮和单位信息面板。
- `UI-INFO-002` 已完成单位信息面板上半部分的截图拟合和回归验证。
- `UI005CaptureSuite` 已存在截图入口，但其 manifest 和覆盖状态仍需要在最终集成任务中扩展。

### 2.2 当前尚不存在

- 没有统一的本地对局玩家列表状态。
- 没有玩家等级、赤金、玩家生命、掉线、准备状态或当前观察目标的权威模型。
- 没有确定性的五槽商店状态、购买、升级、刷新和冻结命令。
- `PlayerState` 没有向玩家单位集合新增购买实例的公开原子命令。
- `StagingHudController` 当前只持有一个本地玩家状态，尚不能在不转移命令权限的前提下显示其他玩家。
- `StateDrivenDeploymentController` 当前把“正在显示的状态”和“允许修改的本地状态”视为同一个来源；直接把它绑定到对手会产生误操作风险。
- `PreparationBattleLoopController` 私有持有临时对手，尚不能向玩家列表和观察 UI 提供统一玩家快照。
- `FormalBattleHudUi005` 没有商店、准备按钮或玩家列表，也没有对外发布完整的“单位信息面板是否打开”事件。
- 商店、准备和玩家列表目录中的独立 PNG 当前仍需在 Unity 内逐项确认 Sprite 导入、透明边缘和拉伸方式。

## 3. 本轮范围

本轮规划完成一个本地数据驱动的 UI 闭环：

```text
固定本地对局数据
→ 多玩家只读列表与本地玩家权威状态
→ 本地商店/等级/赤金/准备状态
→ 商店与准备按钮
→ 观察其他玩家的场地和待部署区
→ 本地玩家仍独占商店和命令权限
→ 30 秒准备—战斗循环
→ 截图、结构化状态与最终视觉报告
```

本轮不实现：

- 网络同步、房间、RPC 或服务器权威；
- 断线检测和重连，只允许用本地测试状态展示掉线图标；
- 完整玩家生命扣除、淘汰和最终胜负结算；
- 未确认的商店概率、经济平衡或升级收益；
- 出售单位；
- 技能、Buff 效果、治疗、护盾或远程单位；
- 观察其他玩家时修改其单位、阵型或商店；
- 为商店或玩家列表重写现有战斗 Core、回放或单位信息面板。

## 4. 开始实现前必须确认的机制

以下问题会影响权威状态、JSON 格式或可观察行为。规划可以先确定任务边界，但 `UI-006` 不得在答案缺失时把推荐值静默固化。

### 4.1 已确认的临时 Demo 数据

- 玩家初始等级为 `1`，最高等级为 `9`。
- 玩家初始赤金为 `7`。
- 玩家初始生命为 `400`。
- 单位源 JSON 和 Player-safe catalog 不增加独立价格字段。商店价格直接等于单位 `rarity`；领域层可以在商品只读快照中暴露计算后的 `Price`，但不得保存第二份可漂移的价格配置。
- 因此 `gopro`（`typeId=1000`，`rarity=1`）价格为 `1`，`arcslma`（`typeId=5503`，`rarity=4`）价格为 `4`。
- 当前 Demo 的升级只执行“扣除赤金并把玩家等级增加 1”，不改变商店概率、待部署容量、部署费用或战斗属性。
- 临时升级费用按当前等级索引固定为：

| 升级 | 赤金费用 |
|---|---:|
| 1 → 2 | 4 |
| 2 → 3 | 6 |
| 3 → 4 | 8 |
| 4 → 5 | 10 |
| 5 → 6 | 12 |
| 6 → 7 | 14 |
| 7 → 8 | 16 |
| 8 → 9 | 18 |

- 等级 `9` 时升级不可用。
- 刷新费用为 `1` 赤金。
- 初始五个商品全部为 `typeId=1000`，允许同一类型重复出现。
- 当前 Demo 不实现免费购买；不创建 `isFree` 状态，不触发 `cost_free.png`。
- 刷新只需确定性地产生玩家可见变化，不实现概率表。临时循环页面固定为：
  1. `[1000, 1000, 1000, 1000, 1000]`；
  2. `[5503, 5503, 5503, 5503, 5503]`；
  3. `[1000, 5503, 1000, 5503, 1000]`；
  4. 返回第 1 页继续循环。
- 刷新时，冻结且仍有商品的槽位保留原商品；其他槽位使用下一页对应索引的类型重新填充。
- 待部署区已有 13 个不可合并槽位时，新购买且无法堆叠的单位进入 `Overflow`。

上述升级费用和刷新页面都是当前本地 UI Demo 的临时确定性配置，不代表最终平衡数值。后续调整配置不得改变购买、升级、刷新命令的原子性和结构化结果。

### 4.2 已确认的准备状态

- 点击“准备就绪”只锁定当前阵型操作，不提前结束准备阶段。
- 准备阶段仍按原有 `30` 秒倒计时进入战斗。
- 点击“取消准备”恢复阵型操作。
- 进入战斗阶段时，等级按钮、商店和准备按钮全部隐藏，并强制关闭已打开的商店。
- 战斗结束返回准备阶段时，准备状态重置为未准备。
- 已准备状态仍允许操作自己的商店。

### 4.3 已确认的玩家观察与双战斗

- 本地 Demo 固定显示 `4` 名本地测试玩家。
- 准备阶段和战斗阶段都允许点击其他玩家头像切换观察目标。
- 每名测试玩家需要独立玩家 ID、显示名、头像资源路径、生命和 `PlayerState`；初始生命统一为 `400`。显示名和头像资源可以由固定测试 JSON 配置，不写死在 UI 组件中。
- 当前固定配对为玩家 1 对玩家 2、玩家 3 对玩家 4；每组前者为 Home，后者为 Away。
- 进入战斗阶段时必须分别计算两场独立战斗，不得把玩家 1/2 的事件流复制给玩家 3/4。
- 点击任意玩家头像时，切换到该玩家所属战斗，并按该玩家在配对中的 Home/Away 身份选择观察视角。
- 两场战斗必须各自只计算一次；切换观察目标不得重新运行战斗 Core。
- 两场结果分别编译为可按任意 Tick 采样的只读表现 Track，并共用一个演示时钟和播放速度；未显示战斗也随该时钟推进。
- 切换时精确恢复位置、生命、护盾、死亡和动作类型；Spine 动画从当前动作类型开头播放，不恢复动画内部进度。
- 较早结束的战斗保持最终状态；全局演示 Tick 到达全部 Battle Track 的最大结束 Tick 后返回准备阶段。
- Damage 只更新 HP Track，不产生 Hit 动作。
- Core 的逐 Tick Move 事件保留完整；表现 Track 使用最大 `1 cm` 误差压缩连续直线移动，并保留已确认的精确关键帧。
- Track 支持任意 Tick 的动态 Spawn；动态单位引用已有 Type ID，并从与 Spawn 绑定的不可变快照读取实例级属性，在每场战斗内从 `-1` 开始确定性递减分配 Unit ID。初始单位可以复用已封存输入中的实例快照。

### 4.4 可以通过截图拟合暂缓

- 等级按钮与设置按钮的最终视觉中心偏移；
- 商店整体和五个槽位的精确 `RectTransform`；
- 商品头像在槽位中的尺寸、裁剪和右上角偏移；
- `frame_outline.png` 放在稀有度边框下是否足够可见；
- 准备按钮背景和边框使用普通拉伸还是九宫格；
- 玩家头像槽位、图标和生命文字的最终像素级间距；
- 掉血背景的持续时间和具体动画。

这些项目不得阻止状态层和结构化 UI 测试，但必须在 `UI-010` 中留下实际截图结论。

## 7. 架构边界

### 7.1 UI-006：本地对局状态

UI-006 应提供一个本地 Demo 对局状态，至少区分：

- 本地玩家 ID；
- 当前观察玩家 ID；
- 每名玩家的只读身份、头像、生命、连接状态和 `PlayerState`；
- 本地玩家的等级、赤金、准备状态；
- 本地玩家的五个商品槽位及冻结状态；
- 稳定递增或可确定生成的购买单位实例 ID；
- 结构化命令结果和可重复的 canonical summary。

必须保持：

- 单位区域、阵型坐标、部署费用、精英化和 Buff 仍由每个玩家自己的 `PlayerState` 维护；
- 商店状态不得塞入 Battle Core；
- 玩家生命和掉线状态暂不触发完整结算或网络逻辑；
- 观察目标只属于本地 UI 会话，不修改被观察玩家；
- 购买成功添加单位时必须走 PlayerState 的原子入口，不能由 UI 直接修改集合；
- 失败命令不得扣赤金、改变商品、增加单位或提高版本号。

推荐的最小商品实例字段：

```text
shopSlotId
unitTypeId
isFrozen
isEmpty
```

商品只读快照可以提供 `Price` 便于 UI 直接显示，但该值每次都由目录条目的 `Rarity` 确定，不属于商品实例或单位 JSON 的独立存储字段。当前 Demo 不创建免费商品实例；`cost_free.png` 保留为未使用资源，不进入业务状态或验收矩阵。

### 7.2 UI-007：商店与准备表现

UI-007 应新增独立、聚焦的商店/准备 HUD 组件，不继续把全部逻辑堆进 `FormalBattleHudUi005`。现有组件继续负责状态栏和单位信息面板，新组件只消费 UI-006 快照并发起命令。

必须遵守：

- 商店显示五个稳定槽位，不以场景子物体顺序作为商品 ID；
- 第一次点击商品只进入二次确认，不立即购买；
- 第二次确认前重新读取最新快照和费用可行性；
- 切换商品、关闭商店、刷新或商品失效时清除旧确认状态；
- 冻结只作用于有商品的槽位，不阻止购买；
- 购买后显示 `bg_empty` 并清除冻结与确认表现；
- 已准备时只锁阵型命令，商店按钮和商店命令仍可使用；
- 准备状态不得通过直接禁用整个 HUD、EventSystem 或 `BattleDemoRoot` 实现。

现有 PNG 的 Sprite 类型、透明度和九宫格边界必须逐项检查。明确弃用资源不得接入，也不得为了“清理”而删除：

- `shop/frozen_icon_lock.png`
- `shop/btn_open.png`

### 7.3 UI-008：显示目标与命令权限分离

UI-008 的核心不是简单替换 `StagingHudController.PlayerState`，而是分离：

```text
LocalCommandPlayerState = 只能由本地部署/撤退/移动命令修改
DisplayedPlayerState    = 当前场地、待部署区和单位信息面板读取的状态
```

必须保证：

- 观察其他玩家时，待部署槽仍可点击查看单位信息，但不能开始拖动；
- 对方已部署单位可以选中查看，但不能开始移动、交换或撤退；
- 本地商店、等级、赤金、部署费用和准备状态不随观察目标切换；
- 观察显示使用 Away/观察者坐标投影，不写回对方一基 `9×4` 阵型；
- 返回自己后恢复本地投影；是否恢复部署操作还要同时检查准备状态和阶段；
- 单位信息面板打开时隐藏 `PlayerListPanel`，关闭或取消选择时恢复；
- UI 隐藏不得清除观察目标、掉线状态或玩家数据。

不允许使用“临时把对方 PlayerState 赋给本地命令控制器，再靠按钮禁用避免误操作”的方案。权限边界必须由接口和测试保证。

### 7.4 UI-009：双战斗编排与可采样表现 Track

进入战斗阶段时，四名测试玩家固定形成两组：

```text
MatchAB = Player1(Home) vs Player2(Away)
MatchCD = Player3(Home) vs Player4(Away)
```

每名玩家的 Overflow 清理和必要自动部署只能执行一次。两组玩家完成阶段封存后，分别生成两份不可变 `BattleInput`，调用既有确定性 Core 得到两份独立结果和事件流。不得为了减少工作而复制输入、事件或胜方。

战斗观察映射为：

```text
Player1 -> MatchAB / Home
Player2 -> MatchAB / Away
Player3 -> MatchCD / Home
Player4 -> MatchCD / Away
```

两份结果分别编译为独立的只读 `BattlePresentationTrack`。每个单位 Track 至少可以按任意演示 Tick 采样位置、朝向、`Idle/Move/Attack/Death` 动作类型、MaxHP、CurrentHP、CurrentShield、Spawn 和死亡状态。动作优先级为 `Death > Attack > Move > Idle`；Damage 只更新 HP，不产生 Hit。

Core 原始事件继续完整保留。Position Track 对逐 Tick Move 进行时间参数化压缩，在每个原始 Move Tick 的误差不得超过 `1 cm`；Spawn、Attack、BlockStarted、BlockEnded、Death、BattleEnded、移动开始、移动停止和最终位置必须精确，不得跨越停顿压缩。

Track 以 Spawn 为单位生命周期起点，允许任意 Tick 创建动态单位。动态单位必须引用已有 Type ID，但 MaxHP、CurrentHP、CurrentShield 和实际战斗属性必须来自与 Spawn 绑定的不可变实例快照；初始单位可以复用已封存 `BattleInput` 中的实例快照。动态 Unit ID 在每场战斗内从 `-1` 开始确定性递减，以 `(BattleId, UnitId)` 作为完整身份，不写回跨回合 PlayerState。

两场 Track 共用一个演示时钟和播放速度。切换观察目标只选择 match、observer 并采样当前 Tick，不重新运行 Core；切换时只恢复动作类型，Spine 从该动作开头播放。较早结束战斗保持最终状态，全局 Tick 到达所有 Track 的最大结束 Tick 后返回准备阶段。

演示层仍不得把任一战斗的 HP、死亡或胜负写回四名玩家的局内 `PlayerState`。

### 7.5 UI-010：统一交互门控与最终集成

部署交互的最终有效条件应由同一处组合，而不是多个组件互相覆盖：

```text
CanMutateFormation =
    Phase == Preparation
    AND IsViewingLocalPlayer
    AND LocalPlayerIsNotReady
```

商店交互的最小条件为：

```text
CanUseShop =
    Phase == Preparation
```

已确认已准备状态不会禁止商店操作。是否允许在观察他人时操作自己的商店，答案为允许；商店始终绑定本地玩家。

进入战斗阶段后等级按钮、商店和准备按钮全部隐藏，商店强制关闭。玩家列表继续显示并负责选择 UI-009 中的战斗观察目标；该选择不得重新开放阵型或商店命令。

#### 验收标准

- 自动加载后无需旧 `InitButton` 即可进入新 HUD。
- 商店、准备状态、观察目标和单位选择不会创建第二份 PlayerState 或改变 Battle Core 结果。
- `CanMutateFormation` 的三个条件均有自动化反例覆盖。
- 同一固定输入重复运行得到相同商店、玩家列表、两份战斗输入、事件和结果摘要。
- 同一固定输入重复运行得到相同 Track 摘要和位置压缩统计；全部 Track 结束后只返回准备阶段一次。
- 截图文件有效，manifest 字段完整，Agent 已逐张打开并记录判断。
- Windows Standalone 构建成功，或明确记录与本任务无关且有证据的阻塞。
- 所有未执行的人工检查明确标记为“未验证”，不得写成通过。

#### 停止条件

- 集成要求新增或猜测经济、扣血、淘汰或多人规则；
- 需要升级 Unity、Package、Input System 或渲染管线；
- 需要覆盖其他未提交的场景、Prefab 或资源改动；
- 连续三次有实质差异的视觉或运行修正仍无法推进。

## 9. 推荐执行顺序

1. 执行 `UI-006`，先稳定四玩家状态和固定商店数据。
2. 执行 `UI-007`，完成本地玩家自己的商店和准备 HUD。
3. 执行 `UI-008`，增加玩家列表和准备阶段观察切换。
4. 执行 `UI-009`，计算两场独立战斗并接通战斗阶段观察。
5. 最后执行 `UI-010`，统一阶段、截图和构建验收。

该顺序优先建立状态和权限边界，再接入表现。它避免商店 UI 自己保存虚假货币/商品状态，也避免观察其他玩家时误把对方状态交给本地部署命令。
