# UI-004：30 秒准备—战斗循环与运行时战斗快照

## 角色

你是本 Unity 项目的本地阶段流程与战斗接入 Agent。

你的职责是建立一个最小、可测试的准备—战斗状态机，把持续存在的 PlayerState 封存为运行时 BattleInput，并交给已有的确定性 Battle Core 和只读 Presentation 播放。演示完成后恢复准备阶段，但绝不把战斗 HP、死亡或胜负写回玩家单位状态。

本任务不是完整回合系统。它只接通当前本地 Demo 所需的 `Preparation → Battle → Preparation` 循环。

## 任务背景

现有战斗 Demo 已能从固定 `unit-catalog-v1 + task004a-real-1v1` 计算并播放真实战斗，但 `BattleDemoCoordinator.Recalculate` 只接受 Resources 路径并重新加载完整固定对战。它没有接收当前内存 PlayerState 生成的 BattleInput 的入口。

UI-001～003 应已经建立持续存在的玩家状态、自动加载、正式待部署 UI、Cost 和状态驱动的手动部署/撤退。现在需要在准备 30 秒后封存状态：先清理 Overflow；若部署区为空则自动部署最高费用且当前 Cost 足够的单位到 `(5,2)`；若仍为空则让固定对手获胜；随后使用现有 Battle Core 和 Presentation 播放，完成后回到准备阶段。

Battle Core 的 20 TPS 与确定性规则不能因回合时钟改变。准备阶段时钟和 Presentation 可以由 Unity 的 unscaled time 驱动，但权威战斗仍必须在播放前完成，并且不依赖 `Time.deltaTime`、Unity Physics 或 Spine 状态。

## 本任务目标

1. 建立一个最小阶段状态模型，至少明确 Loading/Preparation/Battle/Error 或等价内部状态，并对外稳定暴露 Preparation/Battle。
2. 自动加载成功后进入 30 秒 Preparation；无需 InitButton 或战斗 Start 按钮。
3. 准备阶段允许 UI-003 交互；倒计时到 0 后一次性锁定交互并执行转换。
4. 进入战斗时按确认顺序永久移除 Overflow、必要时自动部署最高费用可支付单位到 `(5,2)`、再封存快照。
5. 从当前 PlayerState 和固定真实对手数据构建经现有 BattleInputFactory 验证的运行时输入，不在运行时写临时 JSON。
6. 为 BattleDemoCoordinator/Controller 增加接收已构建 BattleInput 与 UnitCatalog 的最小入口，保留原固定 Resources Demo 兼容入口。
7. 使用已有 BattleRunner 在播放前完成权威计算，再交给已有事件回放和真实单位 Presentation。
8. Battle 演示 Completed 后清理战斗视图、恢复准备阶段视图和交互，并重置新的 30 秒准备倒计时。
9. 保证玩家单位、阵型、精英化、Buff 和当前 Cost 跨阶段保持；战斗 HP、死亡、winner 不写回 PlayerState。
10. 输出本轮输入、Overflow 移除、自动部署、Cost、阶段、Battle 摘要、winner 和错误的结构化日志/状态。
11. 建立无需真实等待 30 秒的阶段测试和一条 SampleScene 完整循环 PlayMode 冒烟。

## 已确认规则

- 准备阶段倒计时固定为 30 秒。
- SampleScene 自动加载玩家状态并自动进入准备阶段。
- 准备阶段结束时禁止继续部署和撤退。
- 阶段转换首先永久移除所有 Overflow 单位。
- 若部署区已有至少一个单位，不触发自动部署。
- 若部署区为空，从待部署区选择部署 Cost 最大且当前 Cost 足够支付的可部署单位，正常扣除 Cost，部署到一基 `(5,2)`。
- 若没有可自动部署单位，则不凭空创建单位，并由另一方获得本场胜利。
- 当前固定测试数据应避免多个单位具有相同最高可支付 Cost 的决胜歧义。
- 战斗使用阶段转换时封存的不可变输入快照。
- Battle Core 固定 20 TPS，与准备倒计时和渲染帧率解耦。
- 演示层只读消费完整战斗结果，不能修改权威输入或结果。
- Battle 播放完成后返回 Preparation，并重新开始 30 秒倒计时。
- PlayerState 生命周期贯穿整局；当前 Cost、单位区域、阵型、精英化和 Buff 保持不变。
- 单场战斗中的当前 HP、伤害和死亡与玩家局内单位状态无关，不写回。

## 不属于本任务的内容

- 不实现商店、赤金、玩家生命扣除、淘汰或完整多回合结算；
- 不实现玩家手动准备/取消准备、多玩家“全部准备”或网络同步；
- 不实现结果停留阶段、奖励、经验、单位升级或阵型重置；
- 不改变 Battle Core 移动、阻挡、攻击、伤害、死亡、maxTicks 或 winner 规则；
- 不把精英化或 UI 字段强行加入 Battle Core，如果当前战斗数值不使用它们；
- 不实现相同最高 Cost 候选的未确认自动部署决胜；
- 不处理双方都无部署单位的长期规则；固定对手必须有有效部署单位；
- 不制作完整 HUD/单位信息面板；UI-005 负责表现收口；
- 不修改 DefaultUnit/TASK-007 血条公式或整体重做 Presentation；
- 不升级 Unity/Package，不安装状态机、Tween、测试或输入第三方依赖。

## 实施要求

### A. 可测试阶段状态机

1. 把阶段状态和倒计时推进放在可独立测试的普通 C# 对象中。Unity MonoBehaviour 只传入 `Time.unscaledDeltaTime`、绑定场景服务和转发状态。
2. 生产准备时长固定配置为 30 秒。测试通过直接 `Advance(seconds)` 或注入时钟推进，不用等待真实 30 秒。
3. 同一阶段只允许一次转换；一帧/一次 Advance 跨过 0 时不能重复清 Overflow、重复扣 Cost 或重复启动战斗。
4. 对外暴露当前阶段、剩余准备秒数、最近转换结果和错误。倒计时不得为负；进入新 Preparation 重置为 30。
5. 初始化/加载失败进入明确 Error，停止时钟和交互，不启动空战斗或显示默认 winner。

### B. Preparation → Battle 转换顺序

6. 到 0 后立即调用 UI-003 交互锁，取消拖拽和选择，再开始状态变更。
7. 调用 PlayerState 的 Overflow 清理并记录永久移除的 unit ID/数量。不能由 UI 隐藏或 BattleInput 过滤代替实际移除。
8. 检查清理后的 Deployed 数量。若大于 0，跳过自动部署。
9. 若为 0，从 Staging 中查找 `deploymentCost <= currentCost` 的候选，选择唯一最高 Cost 候选并通过正常原子部署命令放到 `(5,2)`；成功后 Cost 持续扣除。
10. 当前固定 fixture 必须保证最高可支付 Cost 唯一。若真实输入出现同最高 Cost 多候选，且文档仍无决胜规则，停止并报告，不得依赖 Dictionary/槽插入顺序。
11. 若无可支付候选或 Staging 为空，保持 Deployed 为空并继续构建输入；固定真实对手非空，由已有 Battle Core 正常判 Away/对方胜。不要创建伪单位或在 UI 中硬编码 winner。
12. Overflow 清理和自动部署属于局内玩家状态变化，必须在快照前完成；若阶段转换因数据验证失败，不能悄悄恢复已确认永久移除的 Overflow。对可能失败步骤先做可行性验证并清晰定义提交点，避免半完成状态。

### C. PlayerState → BattleInput

13. 使用当前 Player-safe UnitCatalog，不扫描 `Application.dataPath`、不创建临时 UnitTemplate、不要求 Inspector 手填类型映射。
14. Home 使用当前本地 PlayerState 快照；Away 使用明确的固定真实对手快照。对手来源应版本化、可验证，并复用已有 `local-battle-v1` 数据或从中提取，不复制单位数值。
15. PlayerState 中 Staging/Deployed/Shop 数据按现有 BattleInput 合约转换；Overflow 已在转换前清空，不需要为 Battle Core 新增无关区域枚举。
16. 只有 Deployed 单位参与计算；Staging/Shop 如保留在输入中仍只是状态快照。
17. 使用一基本地阵型坐标，主客场映射继续由已有 BattleInput/Core 负责。不要在 PlayerState 中预先旋转 Away。
18. PlayerState 的精英化目前不改变战斗定义时，不为了“数据完整”扩大战斗规则；在阶段输入摘要中保留玩家快照 digest，明确 Battle Core 当前忽略该 UI/局内字段。
19. 运行时输入必须经过现有验证工厂，拒绝重复 ID、未知 type、非法区域/坐标、重叠和门格。
20. 封存后不得继续读取可变 PlayerState 推进该场战斗。玩家 UI 即使刷新，也不能改变已计算结果。

### D. BattleDemo 运行时入口

21. 为 Coordinator 增加接收已验证 `BattleInput + UnitCatalog + PresentationFactory` 的明确入口，复用现有“计算完成→加载回放→Ready/Playing”的路径，不复制 BattleRunner/Playback 生命周期代码。
22. 保留 `StartOrContinue/Recalculate(Resources paths)` 固定 Demo 行为和现有测试；运行时入口是加法兼容，不删除 TASK-005/006 验收能力。
23. 正式阶段模式下，BattleDemoController 仍是 Coordinator 的唯一 Unity Advance 调用方，避免阶段控制器和 DemoController 同时 Advance 播放。
24. 对 Coordinator 状态提供事件或稳定查询，使阶段控制器能在 `Completed` 后只转换一次。Error 时进入阶段 Error 并输出原因，不自动重试无限循环。
25. BattleDemoUI 默认隐藏时仍可调试查看，但正式阶段模式下不得让 `Recalculate` 按钮绕过 PlayerState 重启旧固定输入。暂停/速度/观察视角如果保留，必须只影响当前封存回放。
26. Replay 只重播同一封存结果，不重新清 Overflow、自动部署或扣 Cost。

### E. Battle → Preparation

27. 只在 Presentation 真正 `Completed` 后结束 Battle；不能在 Core 计算完成时立即返回准备。
28. 转换时清理 BattleDemoViews/Playback，恢复或重建 UI-003 的 PreparationUnitViews，使它们反映持续存在的 PlayerState 阵型。
29. 不应用 BattleRunResult 的当前 HP、Alive/Death 或 winner 到 PlayerState。自动部署和 Overflow 清理仍保留，因为它们发生在战斗快照之前。
30. 重新启用准备交互并把倒计时重置为 30。不得重新加载本地玩家 JSON覆盖内存状态。
31. 输出阶段结束摘要：battle ID、input digest、event/result digest、winner/reason、PlayerState before/after digest，并断言玩家单位/Cost 仅包含允许的阶段前变更。

### F. 生命周期和收尾

32. Scene reload、OnDisable、OnDestroy 时清理状态机订阅、Coordinator 状态订阅和临时视图；不留下静态 PlayerState 或双重 Update。
33. 同一 SampleScene 中只能有一个正式阶段控制器。若用 Editor 接线，确保幂等。
34. 审查场景和代码 diff，保持旧固定战斗测试入口可用。
35. 更新文档记录真实阶段和运行时 BattleInput 数据流。

## 验证要求

### 自动验证

至少覆盖：

- 初始化成功进入 Preparation，剩余 30 秒；
- Advance 未到 0 不转换，到 0 只转换一次；
- 转换前交互被锁，进行中的拖拽被取消；
- Overflow 单位全部且只被永久移除；
- 已有 Deployed 时不自动部署；
- 空 Deployed 时选择唯一最高可支付 Cost 单位，部署到 `(5,2)` 并正常扣费；
- 高价单位不可支付时选择下一个可支付的最高 Cost；
- 无可支付/无 Staging 时不部署，固定非空 Away 输入得到 Away/对方胜；
- 生成输入使用一基坐标、真实 type、固定对手并通过现有验证；
- 封存后修改/刷新 PlayerState 不改变已生成 input digest 或 result；
- Battle 只在 Presentation Completed 后回 Preparation；
- 返回后 Cost/阵型/精英化/Buff 保留，Battle 死亡/HP 不写回；
- 新 Preparation 倒计时恢复 30；
- Replay 不重复 Overflow 清理、自动部署或扣费；
- 运行时入口和旧固定 Resources 入口均保持现有回归结果。

PlayMode 至少覆盖一条 SampleScene 完整流程。测试通过直接推进阶段时钟，不真实等待 30 秒；真实单位视图、BattleEnded、回到 Preparation、准备视图恢复和无残留都要有结构化断言。

### 人工检查

1. 进入 SampleScene，确认自动处于 Preparation 和 30 秒；
2. 手动部署/撤退一次，确认时钟不受影响；
3. 保持部署区为空等待转换，观察 Overflow 清理、最高费用可支付单位自动到 `(5,2)` 和 Cost 扣除；
4. 检查正式交互在 Battle 中锁定；
5. 确认 Core 先完成、Presentation 正常播放；
6. 等待播放 Completed，确认返回 Preparation、30 秒重置和原阵型恢复；
7. 确认战斗中死亡单位回到准备阵型，Cost 未因死亡变化；
8. 打开调试面板检查 input/event/result digest 和 winner；
9. Replay 当前结果，确认不重复扣费或清 Overflow；
10. 退出重进检查没有重复状态机、视图或订阅。

### 无法执行时

无法可靠等待/观察 GUI 时，必须提供纯状态机时间推进、输入/结果 digest、PlayerState 前后摘要和 PlayMode 结构化证据，并把人工视觉流程写为“未验证”。
