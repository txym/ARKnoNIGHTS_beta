# LAN 房间界面与本地房间闭环设计

## 目标与范围

为 `SampleScene` 新增一套独立于战斗 Core 的局域网房间入口，复刻参考图 9 的深色终端主界面与参考图 10 的房间卡片布局。目标平台为同一局域网内的 Windows 与 Android；不依赖第三方网络包、账号、云服务或外网。

本任务只同步房间成员、昵称、头像索引、准备状态、延迟和“开始”信号。所有玩家准备后由主机发起开始，各端关闭房间 UI 并进入已有的本地战斗演示。部署、商店、战斗事件、胜负与玩家数据均不跨机同步，不能表述为联网对战。

## 非目标

- 不实现互联网连接、NAT 穿透、账号、匹配服务或房间持久化。
- 不实现跨端部署、商店、战斗结果或断线重连。
- 不复刻参考图 9 左上/左下、左侧雷达大小，或参考图 10 左上和底部中间“不搜寻队友｜终极模拟”区。
- 不复刻图 10 中的玩家立绘；房间卡只使用统一的头像、状态、名称与装饰框。

## 素材来源约束

除非某张贴图明确由 Codex 为本任务生成，所有用于复刻界面的贴图都必须直接来自用户指定的素材库：`G:\素材\11.14\Unpacked_1763129662\Android\ui\autochess`。不得使用网络图片、其他本地目录的贴图、临时占位图片或从参考截图裁切的图片来冒充素材库资源。导入到项目的每一张贴图必须在素材映射文档中记录其源文件相对路径和用途。

## 用户体验与视觉

### 主界面

场景启动时显示全屏深色网格、扫描纹理和青绿色边框。右侧使用两张大型终端风格操作卡：`创建房间` 为青绿色，`加入房间` 为橙色。加入区包含房间号输入框、已发现房间列表和确认按钮。

左侧放置风格一致的本地身份卡：头像选择器、昵称输入框和保存动作。昵称及头像索引保存到本机偏好设置；不写入战斗 `PlayerState`。

创建时生成六位数字房间号，主界面立即进入房间页。已发现房间的条目显示房间号、房主昵称、人数和加入状态；点击条目只将该房间号预填到输入框，仍需按 `加入房间` 确认。

### 房间页

房间最多四张玩家卡，按加入顺序从左到右排列。每张卡显示头像缩略图、昵称、主机标志（仅首位）、准备/未准备状态和延迟；左上角总是显示本机延迟。卡片使用青绿色准备边框及暗灰色未准备边框，避开参考图中的人物立绘。

玩家只能切换自己的准备状态。主机可以解散房间；当所有已连接成员准备后，主机可开始。客户端在等待开始时显示明确状态。离开或断线后，主机将该成员移除并更新房间广播。

房间 UI 存在期间，现有 `PreparationBattleLoopController` 的自动准备倒计时必须被一个明确的只读“大厅门控”暂停，不能在玩家仍处于房间内时于后台开始本地战斗。收到主机 `Start` 后，各端在同一帧解除门控、关闭大厅 Canvas，并把现有准备循环重置到它原有的 30 秒准备入口；之后仍遵循当前单机循环，且不向房间回写战斗状态。

## 网络设计

### 发现和连接

主机在固定 UDP 发现端口周期性广播小型、版本化的房间公告：协议版本、房间号、房主昵称、成员数、容量、是否可加入、TCP 端口和序列号。客户端只在本局域网监听并维护过期的发现条目；网络端点只在内部使用，UI 不显示 IP 或端口。

客户端用输入房间号在当前发现条目中查找主机，再建立一条 TCP 会话。若房间号未发现、已满或已开局，UI 留在主界面并给出对应错误。主机拒绝未知协议版本、重复会话、满房和开始后的加入请求。

房间号由主机随机生成，限定为该局域网、该主机生命周期内有效。发现到同房间号但不同主机会被视为冲突，主机重新生成并重新公告。

### 房间状态与消息

房主维护唯一权威 `LobbyRoomSnapshot`。成员仅可请求修改自己的昵称、头像索引和准备状态。主机广播完整快照，客户端只渲染快照，不自行推导成员或准备状态。

TCP 消息为长度前缀 JSON，包含协议版本、消息种类及有界字段。消息种类限定为：`JoinRequest`、`JoinAccepted`、`RoomSnapshot`、`SetReady`、`Ping`、`Pong`、`Start`、`Leave` 与 `Reject`。每秒心跳一次，以往返时间更新延迟；连续超时则断开并清理。

### 生命周期与平台

离开房间、返回主界面、场景卸载或应用退出会取消 UDP 广播、关闭 TCP listener/client、取消后台任务并清空仅运行时房间状态。无需后台服务。

Windows 与 Android 均使用 .NET socket API。Android 在连接页期间申请 Wi-Fi multicast lock，降低局域网发现被系统过滤的风险；Android manifest 需包含互联网及 Wi-Fi multicast 所需权限。Windows 防火墙必须允许该应用在专用网络收发 UDP/TCP。真实双端连通性属于设备验收，不能仅凭 Editor 测试声明通过。

## 组件边界

- `ARKnoNIGHTS.Lobby`：协议 DTO、房间号、快照、连接状态、可测试的消息编解码、Android multicast lock 抽象以及无场景依赖的大厅布局/视图；不得依赖 Battle Core。
- `LanRoomHost` / `LanRoomClient`：负责 UDP/TCP、取消、超时、线程切换和向上层发布只读快照；不得修改战斗数据。
- `LanLobbyController`：唯一的 Unity 会话协调器，控制主界面、房间页、身份偏好、`PreparationBattleLoopController` 的大厅门控与战斗入口切换。
- `LanLobbyView`：归入 `ARKnoNIGHTS.Lobby`，只创建与刷新 uGUI 视图，使用新导入的 `autochessouter` 素材和直接加载的正式字体资源；不保存第二份业务状态。

现有 `PlayerState`、`PreparationBattleLoopController`、`FormalBattleHudUi005` 和 Battle Core 不承载网络房间状态。该任务不修改当前已有的脏工作树文件、场景或 Prefab；需要接线时采用新增启动组件或待后续稳定工作树中的最小编辑。

## 错误处理与安全边界

- 所有网络输入均视为不可信：限制消息大小、昵称长度、房间号格式和头像索引；无效 JSON、未知消息、协议不匹配或非法状态转换一律拒绝并记录非敏感诊断。
- 不执行或下载网络数据，不上传源码、资源、日志或身份信息。
- 网络失败、房满、房间已开始、广播不可用、端口占用和防火墙阻断都呈现为可恢复 UI 状态；不以静默本地模式冒充成功连接。
- 任何连接失败或成员离开均不修改已有战斗/玩家权威状态。

## 验证

1. EditMode：房间号有效性与冲突、发现条目过期、消息编解码/长度限制、主机状态机、准备权限、满房/开局拒绝与超时清理。
2. PlayMode：主界面/房间页切换、发现条目点击预填、加入失败提示、四张房间卡、昵称/头像持久化、准备状态和延迟文本刷新。
3. 本机 socket 冒烟：主机与客户端独立实例互相发现、加入、准备、开始、离开和端口释放。
4. Windows + Android 同一 Wi-Fi 手工验收：双方发现、以房间号加入、准备、延迟显示、开始、断开和恢复到主界面。若防火墙、路由器隔离或 Android 权限阻止发现，明确标记为未验证/失败，不以 Editor 结果替代。

## 停止条件

如需新增第三方网络包、外网/云服务、账户凭据、Unity/Package 升级，或发现现有战斗入口只能通过大范围修改脏工作树接入，则停止并取得批准或等待稳定集成点。
