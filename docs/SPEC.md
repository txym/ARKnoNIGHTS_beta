# 项目需求与游戏机制规范

> **文档状态：持续完善中（Draft）**  
> 本文档用于记录项目目标、核心流程和已经确认的游戏机制。当前尚未描述的规则将在后续开发过程中逐步补充。  
> 凡涉及玩家可见行为、数值结算、回合流程、胜负条件或多人同步的规则，如本文档未明确说明，实施前应先向项目负责人确认，不得自行推测。

## 1. 项目概述

本项目是一款以《明日方舟》为题材的同人自走棋游戏 Demo。

项目目前仍处于早期开发阶段，尚未实现完整的多人联机流程。现阶段已经搭建了基础战斗场景，后续工作的重点是逐步完善战斗系统、回合流程和相关交互。

## 2. 项目目标

### 2.1 长期目标

制作一个可供 4 名玩家通过局域网联机游玩的自走棋 Demo。

### 2.2 当前阶段目标

当前阶段优先完成以下内容：

- 完善单个战斗场景中的准备阶段和战斗阶段；
- 建立清晰、可扩展的回合状态流转；
- 完善单位部署、交换、阻挡、攻击和结算等核心机制；
- 为后续多人联机、状态同步和完整对局流程预留合理接口；
- 建立能够验证核心游戏机制的测试与调试手段。

## 3. 核心术语

- **至纯源石**：局内货币资源，可用于在商店中购买单位。其具体获取方式、消耗规则和是否承担其他用途，后续补充。
- **待部署区**：用于临时存放玩家已拥有但尚未部署到战场上的单位。
- **部署区**：玩家可放置单位并形成战斗阵型的区域。
- **阵型**：玩家在准备阶段结束时保存的已部署单位及其位置。
- **准备阶段**：玩家购买、部署和调整单位的阶段。
- **战斗阶段**：阵型锁定后，单位自动移动、攻击并完成战斗结算的阶段。

## 4. 整体游戏流程

完整对局的预期流程如下：

1. 玩家在主界面创建房间。
2. 其余玩家通过局域网加入该房间。
3. 房间内达到 4 名玩家后，由房主点击“开始游戏”。
4. 所有玩家进入游戏场景。
5. 单局游戏由若干回合组成。
6. 每个回合包含准备阶段和战斗阶段。
7. 战斗结束后，根据结算规则扣除相关玩家的生命值。
8. 对局持续进行，直至只剩一名玩家未被淘汰。
9. 最后一名未被淘汰的玩家获得胜利。

> 房间加入方式、人数不足时能否开始、断线重连、淘汰后的行为以及胜负结算细节，后续补充。

## 5. 回合流程

### 5.1 准备阶段开始

准备阶段开始时，系统根据该玩家当前保存的数据，重置并恢复场地中的单位和阵型状态。

需要恢复的数据至少包括：

- 玩家拥有的单位；
- 待部署区中的单位；
- 已部署单位及其位置；
- 单位对应的部署费用状态；
- 其他需要跨回合保留的数据。

具体数据结构和跨回合保留规则后续补充。

### 5.2 准备阶段可执行操作

准备阶段中，玩家可以进行以下操作。

#### 5.2.1 在商店中购买单位

玩家可以消耗“至纯源石”购买单位。

购买成功后：

1. 若待部署区仍有空位，单位优先进入待部署区。
2. 若待部署区已满，则玩家需要在部署区选择一个允许部署的位置。
3. 单位成功放置到部署区后，扣除对应的部署费用。

以下规则后续补充：

- 商店刷新方式；
- 单位价格；
- 待部署区容量；
- 部署费用的资源类型；
- 部署区无可用位置时的处理方式；
- 购买过程中取消操作的处理方式。

#### 5.2.2 将单位从待部署区部署到部署区

玩家可以将待部署区中的单位放置到部署区的有效位置，并扣除该单位对应的部署费用。

若玩家尝试将待部署区中的单位 A 部署到已经存在单位 B 的位置，则按照以下顺序处理：

1. 将单位 B 返回待部署区；
2. 返还单位 B 已消耗的部署费用；
3. 将单位 A 部署到该位置；
4. 扣除单位 A 的部署费用。

以下情况尚需明确：

- 待部署区已满时，单位 B 是否仍可被替换；
- 单位 A 部署失败时，是否需要恢复操作前状态；
- 部署费用不足时是否允许发起替换；
- 不同单位是否存在部署区域或地形限制。

#### 5.2.3 交换部署区中的单位位置

玩家可以交换两个已部署单位的位置。

交换操作原则上不改变玩家已拥有的单位，也不额外扣除或返还部署费用。

单位位置限制、交换失败条件和动画表现后续补充。

#### 5.2.4 准备就绪与取消准备

玩家点击“准备就绪”后：

- 禁止继续购买单位；
- 禁止继续部署单位；
- 禁止继续交换单位位置；
- 当前阵型保持不变；
- 在战斗阶段正式开始前，玩家可以取消准备并恢复上述操作权限。

取消准备的截止时间和多人状态同步方式后续补充。

### 5.3 从准备阶段进入战斗阶段

满足以下任一条件时，准备阶段结束：

- 所有玩家均已准备就绪；
- 准备阶段倒计时结束。

准备阶段结束后：

1. 禁止玩家继续修改阵型；
2. 保存每名玩家当前的已部署单位及其位置；
3. 将游戏状态切换为战斗阶段；
4. 开始执行战斗阶段初始化流程。

### 5.4 战斗阶段

战斗阶段开始后：

1. 敌我双方单位分别从红门和蓝门进入场地；
2. 单位向对应阵型位置移动；
3. 等待预定的战斗开始时间；
4. 单位按照战斗系统规则自动进行战斗；
5. 玩家不能直接操作战斗中的单位。

红门、蓝门的阵营含义、移动路径、入场顺序、等待时间和异常处理方式后续补充。

### 5.5 战斗结算

战斗结束后，系统根据结算规则扣除相关玩家的生命值。

结算完成后：

1. 判断是否有玩家被淘汰；
2. 判断是否已经满足整局游戏的胜利条件；
3. 若对局尚未结束，则进入下一回合的准备阶段；
4. 若只剩一名玩家未被淘汰，则结束本局游戏。

具体扣血公式、平局处理、超时处理和淘汰规则后续补充。

## 6. 玩家可随时执行的操作

除非后续规则另有说明，玩家可以随时进行以下操作：

- 点击玩家头像，切换当前场地中显示的玩家内容；
- 打开或关闭商店界面。

需要进一步确认：

- 战斗阶段能否浏览其他玩家场地；
- 战斗阶段能否打开商店但禁止购买；
- 切换观察对象是否影响本地输入、镜头或界面状态。

## 7. 战斗系统

战斗机制可参考 [PRTS Wiki：作战机制](https://prts.wiki/w/%E4%BD%9C%E6%88%98%E6%9C%BA%E5%88%B6#%E4%BC%A4%E5%AE%B3%E5%8F%8A%E5%85%B6%E5%A4%84%E7%90%86)。

该页面仅作为设计参考。若外部资料、现有代码和本文档之间存在冲突，应以本文档中已经确认的规则为准；本文档未明确的机制不得直接照搬原作，应先向项目负责人确认。

### 7.1 逻辑帧

当前暂定规则为：

- 每 3 个游戏帧执行一次战斗逻辑判定；
- 移动、阻挡、攻击和其他战斗行为原则上在逻辑帧中更新。

> “每 3 帧”的实现口径仍需进一步确认，例如是否依赖实际渲染帧率，或改为基于固定时间步长的逻辑更新。确认前不得自行改变该规则的含义。

### 7.2 碰撞与阻挡

- 单位碰撞范围暂按半径为 `0.25` 格的圆形区域计算；
- 系统根据碰撞范围判断单位是否发生阻挡；
- 被阻挡的单位只能攻击其阻挡来源；
- 每个单位具有“阻挡数”属性；
- 每个被阻挡单位会占用一定数量的阻挡数。

以下规则后续补充：

- 多个单位同时进入阻挡范围时的优先级；
- 阻挡关系的建立和解除条件；
- 阻挡数不足时的行为；
- 空中单位、不可阻挡单位等特殊情况；
- 单位死亡、位移或传送时的阻挡关系清理。

### 7.3 攻击数据

单位每次攻击都会生成一份攻击属性数据，用于描述并处理本次攻击。

攻击数据至少可能包含：

- 攻击力；
- 攻击类型；
- 是否致死；
- 是否属于环境伤害；
- 攻击来源；
- 攻击目标；
- 其他用于伤害、效果和结算的属性。

攻击数据的完整字段、生命周期、修改顺序和结算流程后续补充。

## 8. 规则优先级与不确定性处理

规则解释优先级如下：

1. 项目负责人在当前任务中的明确说明；
2. 本文档中已经确认的规则；
3. `docs/decisions/` 中已接受的设计决策；
4. 当前实现和现有测试所体现的行为；
5. 外部参考资料。

当出现以下情况时，应暂停相关实现并向项目负责人确认：

- 玩家可见行为不明确；
- 数值、费用或结算方式不明确；
- 回合状态转换不明确；
- 多人同步的权威端和冲突处理方式不明确；
- 胜负、淘汰或异常情况的处理方式不明确；
- 本文档、现有代码、测试或外部资料互相冲突。

对于不影响游戏规则和玩家可见行为的低风险实现细节，可以采用最小、可逆且符合现有代码风格的方案，但必须在任务汇报中说明所作假设。

## 9. 当前阶段验收原则

在更完整的测试规范建立前，当前阶段至少应满足：

- Unity 项目能够正常编译；
- 战斗场景能够正常进入和退出；
- 准备阶段与战斗阶段能够按照明确状态切换；
- 已实现的部署、交换和准备操作符合本文档中的规则；
- 战斗开始后玩家无法继续修改阵型；
- 战斗结束后能够进入结算或下一回合；
- 不存在未处理异常或被静默忽略的严重错误；
- 对尚未实现或规则未明确的部分进行明确记录，不得伪装为已经完成。
