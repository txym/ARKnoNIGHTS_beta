# 项目需求与游戏机制规范

> **文档状态：持续完善中（Draft）**  
> 本文档用于记录项目目标、核心流程和已经确认的游戏机制。当前尚未描述的规则将在后续开发过程中逐步补充。  
> 凡涉及玩家可见行为、数值结算、回合流程、胜负条件或多人同步的规则，如本文档未明确说明，实施前应先向项目负责人确认，不得自行推测。

## 1. 项目概述

本项目是一款以《明日方舟》为题材的同人自走棋游戏 Demo。

项目目前仍处于早期开发阶段，尚未实现完整的多人联机流程。现阶段已经搭建了基础战斗场景，后续工作的重点是逐步完善战斗系统、回合流程和相关交互。

## 2. 项目目标

### 2.1 长期目标

制作一个可供 4 名玩家通过局域网联机游玩的自走棋 Demo。

### 2.2 当前阶段目标

当前第一阶段优先完成由一名本地玩家驱动的单机战斗验证版本，暂不实现准备阶段、商店购买、完整回合循环和多人同步。第一阶段优先完成以下内容：

- 建立与 Unity 物理和渲染帧率解耦的战斗计算流程；
- 根据测试对战数据初始化敌我双方单位和阵型；
- 完成移动、索敌、阻挡、攻击、伤害、死亡和单场战斗胜负判定；
- 将预先计算得到的战斗内容交给演示层播放单位移动和动画；
- 在单位脚下显示与观察者阵营一致的世界空间血量/护盾状态条；
- 为后续准备阶段、多人联机、状态同步和完整对局流程预留合理接口；
- 建立能够验证战斗结果和演示一致性的测试与调试手段。

准备阶段、商店、部署交互、完整回合循环和多人联机仍属于项目目标，但不属于当前第一阶段的完成条件。

### 2.3 当前 UI 接入阶段

在第一阶段固定单场战斗闭环之后，当前 UI 接入阶段增加一个由本地测试玩家数据驱动的最小“准备阶段 → 战斗阶段 → 准备阶段”循环。该循环用于把玩家状态、待部署区、手动部署、战斗输入快照和现有战斗演示接通，不代表完整回合、商店、玩家扣血或多人同步已经实现。

当前 UI 接入阶段至少包括：

- 场景进入后自动加载本地玩家测试数据，不再依赖 `InitButton`；
- 本地玩家拥有贯穿整局游戏生命周期的玩家状态；
- 准备阶段倒计时固定为 `30` 秒；
- 倒计时结束后锁定阵型、执行进入战斗阶段的清理和自动部署规则，并从玩家状态生成本场战斗输入快照；
- 战斗演示播放结束后返回准备阶段；
- 单场战斗中的受伤和死亡不写回局内玩家单位状态。

本阶段仍不实现商店购买、赤金变化、玩家生命扣除、完整回合结算和多人功能。

## 3. 核心术语

- **赤金**：局内货币资源，可用于在商店中购买单位。撤离场上单位不会返还赤金；出售单位时会返还一定比例的赤金，具体比例后续补充。
- **部署费用**：与赤金相互独立的战斗资源。部署单位会占用部署费用，撤离单位会返还其已占用的 `100%` 部署费用。
- **待部署区**：用于临时存放玩家已拥有但尚未部署到战场上的单位。
- **部署区**：玩家可放置单位并形成战斗阵型的区域。
- **阵型**：玩家在准备阶段结束时保存的已部署单位及其位置。
- **准备阶段**：玩家购买、部署和调整单位的阶段。
- **战斗阶段**：阵型锁定后，单位自动移动、攻击并完成战斗结算的阶段。
- **战斗计算**：根据确定的输入数据，使用离散逻辑帧预先计算单位行动、状态变化和战斗结果的过程。战斗计算不依赖 Unity 物理碰撞或渲染帧率。
- **战斗演示**：读取战斗计算结果并播放单位移动、动画和其他表现的过程。演示结果不得反向影响战斗计算结果。
- **主场方**：一场配对战斗中，其阵型坐标直接作为本场战斗基础坐标的一方。
- **客场方**：一场配对战斗中，其阵型需要旋转到对面半场后参与战斗的一方。

### 3.1 战斗场地与坐标

- 战斗场地由 `9 × 8` 个格子组成。
- 所有游戏规则坐标统一使用一基坐标，横坐标范围为 `1..9`，纵坐标范围为 `1..8`。
- 单个玩家保存的阵型使用 `9 × 4` 的本地阵型坐标，横坐标范围为 `1..9`，纵坐标范围为 `1..4`。
- 玩家阵型缓存始终保存本地阵型坐标，不因观察其他玩家或参加客场战斗而修改。
- 蓝方半场为第 `1..4` 行，红方半场为第 `5..8` 行。
- 蓝门位于 `(5,1)`，红门位于 `(5,8)`；两个门格均不可部署单位。
- 以战斗场地中心为基准进行 `180` 度旋转时，坐标按 `(x, y) -> (10 - x, 9 - y)` 转换。
- 非战斗阶段浏览其他玩家阵型时，只在显示层将被观察玩家的阵型旋转并显示到红方半场，不修改被观察玩家的阵型缓存。
- 配对进行战斗时，系统从双方中确定主场方和客场方。主场方阵型直接放置在蓝方半场，客场方阵型经过上述旋转后放置在红方半场，战斗计算以该主场坐标系进行。
- 主场方观察战斗时可以直接播放战斗计算结果；客场方观察同一场战斗时，需要在演示层对战斗内容中的坐标和方向再次执行上述旋转。该显示变换不得修改原始战斗计算结果。

## 4. 整体游戏流程

完整对局的预期流程如下：

1. 玩家在主界面创建房间。
2. 其余玩家通过局域网加入该房间。
3. 房间内达到 4 名玩家后，由房主点击“开始游戏”。
4. 所有玩家进入游戏场景。
5. 单局游戏由若干回合组成。
6. 每个回合包含准备阶段和战斗阶段。
7. 战斗结束后，根据结算规则扣除相关玩家的生命值。
8. 对局持续进行，直至只剩一名玩家未被淘汰。
9. 最后一名未被淘汰的玩家获得胜利。

> 房间加入方式、人数不足时能否开始、断线重连、淘汰后的行为以及胜负结算细节，后续补充。

当前第一阶段只实现单场战斗验证，可以绕过准备阶段和完整对局流程，通过测试对战数据直接开始战斗。完整对局流程仍作为后续阶段目标保留。

## 5. 回合流程

### 5.1 准备阶段开始

准备阶段开始时，系统根据该玩家当前保存的数据，重置并恢复场地中的单位和阵型状态。

需要恢复的数据至少包括：

- 玩家拥有的单位；
- 待部署区中的单位；
- 已部署单位及其位置；
- 单位对应的部署费用状态；
- 其他需要跨回合保留的数据。

当前本地 UI Demo 中，玩家状态的生命周期贯穿整局游戏，而不是在准备阶段和战斗阶段之间重建。玩家状态至少维护：

- 当前可用部署费用；
- 玩家拥有的单位实例；
- 每个单位的独立单位 ID、`type ID`、当前区域、精英化等级和 Buff；
- 已部署单位的一基本地 `9 × 4` 阵型坐标。

本地测试玩家的初始可用部署费用为 `99`。部署费用在阶段切换时保持不变：部署成功时扣除对应费用，撤退成功时返还 `100%` 已占用费用，进入或退出战斗阶段不会自动重置为 `99`。

单位类型 JSON 需要包含初始精英化等级。单位实例创建到玩家状态后独立保存自己的当前精英化等级；UI 读取玩家单位实例状态，不把类型 JSON 当作运行时精英化状态的权威来源。

当前确认的真实单位初始精英化等级为：`gopro`（`1000`）=`0`，`arcslma`（`5503`）=`0`。不得由稀有度推断该字段。

### 5.2 准备阶段可执行操作

准备阶段中，玩家可以进行以下操作。

#### 5.2.1 在商店中购买单位

玩家可以消耗“赤金”购买单位。

购买成功后：

1. 若待部署区存在可合并的同类型单位堆叠，则新单位优先加入该堆叠。
2. 若不存在可合并堆叠但待部署区仍有空位，则单位进入新的待部署槽位。
3. 若不存在可合并堆叠且待部署区已经达到 `13` 个槽位，则新单位进入 `Overflow`。
4. 每个购买得到的单位仍具有独立单位 ID；购买不会直接把单位部署到场上，也不会扣除部署费用。

单位类型源 JSON 和 Player-safe catalog 均不保存独立的商店价格字段。商品价格直接等于单位稀有度 `rarity`；领域层或 UI 只读快照可以暴露派生的 `Price` 便于显示，但该值必须每次由 `Rarity` 计算，不得保存第二份可能与稀有度漂移的配置。当前 `gopro`（`1000`）稀有度为 `1`，商品价格为 `1`；`arcslma`（`5503`）稀有度为 `4`，商品价格为 `4`。

当前本地 UI Demo 使用以下临时确定性配置：

- 玩家初始等级为 `1`，最高等级为 `9`；
- 玩家初始赤金为 `7`；
- 玩家初始生命为 `400`；
- 五个初始商品全部为 `typeId=1000`，同一类型允许重复出现；
- 当前 Demo 不实现免费购买；
- 刷新消耗 `1` 赤金；
- 刷新商品使用固定循环页面：
  1. `[1000, 1000, 1000, 1000, 1000]`；
  2. `[5503, 5503, 5503, 5503, 5503]`；
  3. `[1000, 5503, 1000, 5503, 1000]`；
  4. 返回第 1 页；
- 冻结只作用于当前有商品的槽位；刷新时保留冻结且尚未购买的商品，其他槽位读取下一页对应索引；
- 冻结不禁止购买；冻结商品购买成功后槽位变为空并清除冻结状态。

当前 Demo 的玩家升级只扣除赤金并把等级增加 `1`，不改变商店概率、待部署容量、部署费用或战斗属性。临时升级费用为：`1→2=4`、`2→3=6`、`3→4=8`、`4→5=10`、`5→6=12`、`6→7=14`、`7→8=16`、`8→9=18`；等级 `9` 时不能继续升级。这些数值只用于本地 UI Demo，不代表最终平衡。

以下规则后续补充：

- 购买过程中取消操作的处理方式；
- 最终商店生成概率、升级效果和经济平衡；
- 出售单位时赤金的返还比例。

#### 5.2.2 将单位从待部署区部署到部署区

玩家可以将待部署区中的单位放置到部署区的有效位置，并扣除该单位对应的部署费用。

待部署区按照槽位计算容量，上限为 `13` 个槽位：

- 单位堆叠只存在于待部署区，部署区和商店不使用待部署区的堆叠规则；
- 无法堆叠的单位占用一个槽位；
- 一个单位堆叠占用一个槽位，堆叠中的单位数量显示在单位头像右下角；
- 只有 `type ID`、精英化等级和拥有的 Buff 完全一致的单位才能进入同一堆叠；
- 每个单位仍然具有独立的单位 ID；
- 单位的基础数据由 `type ID` 对应的数据定义，单位 ID、所在区域、精英化等级和 Buff 等实例状态仍需保留。

待部署区显示的是严格堆叠后的槽位，而不是为每个单位实例单独建立一个槽位。玩家状态层负责产生稳定的有序堆叠槽快照，UI 不自行维护另一份顺序。有序槽位从左到右按照以下字段排列：

1. 部署费用升序；
2. 部署费用相同时，按 `type ID` 升序。

同费用、同 `type ID` 但因精英化等级或 Buff 不同而不能堆叠的多个槽位之间的最终决胜顺序尚未确认；当前固定测试数据应避免依赖该顺序。

Buff 的效果、语义等价和规范化规则仍未确认。当前本地测试状态只使用空 Buff；玩家状态保留原始 Buff 快照，并且只在完整快照逐项一致时允许严格堆叠，不据此定义任何 Buff 的游戏效果。

若玩家尝试将待部署区中的单位 A 部署到已经存在单位 B 的位置，则先进入替换预览，不立即修改单位池、阵型或资源。玩家确定单位 A 和单位 B 后，系统统一进行以下可行性检查：

1. 按照“单位 A 离开待部署区、单位 B 依照严格堆叠规则返回待部署区”的完整预期结果计算，待部署区是否会超过容量上限；
2. 假设返还单位 B 已占用的全部部署费用后，玩家是否有足够部署费用放置单位 A。

部署费用不足不禁止玩家发起和预览替换操作，只会使最终确认失败。待部署区超过容量上限时，最终确认同样失败。

确认失败时，单位 A、单位 B、玩家单位池、阵型和资源均保持不变，只更新 UI 中的失败状态。确认成功后，以下变更作为一次完整操作生效：

1. 将单位 B 撤离并返回待部署区；
2. 返还单位 B 已占用的 `100%` 部署费用；
3. 将单位 A 部署到目标位置；
4. 扣除单位 A 对应的部署费用。

以下情况尚需明确：

- Buff 完全一致的精确比较字段和规则；
- 同费用、同 `type ID` 的不同严格堆叠槽之间的最终排列规则；
- 替换失败时 UI 的具体表现；
- 不同单位是否存在部署区域或地形限制。

#### 5.2.3 交换部署区中的单位位置

仅在准备阶段，玩家必须先选中一名已部署单位，随后才能拖动该已选中单位调整位置。第一次点击已部署单位只负责选中；未选中的单位不能在同一次首次手势中直接换位。

将已选中单位拖到空的合法部署格时，该单位移动到目标格；拖到另一名己方已部署单位所在格时，两名单位原子交换一基本地阵型坐标。拖回自己的原格视为成功的 no-op，不改变玩家状态版本，也不发出状态变化通知。

目标坐标超出本地 `9 × 4` 范围、落在蓝门 `(5,1)` 或无法解析时操作失败，阵型、部署费用、状态版本和状态通知均保持不变。移动、交换、失败和同格 no-op 均不扣除、返还或重新判断部署费用。

拖动期间场景预览不得提前修改玩家状态；松手时只提交一次状态命令。开始拖动已选中单位时，必须暂时隐藏其 `DeployedUnitSelectionIndicator`；成功、失败、同格 no-op 或常规取消结束后，只要该原始 `unit ID` 仍保持选中，就重新显示并绑定该选择效果，而非绑定目标格或被交换单位。准备阶段交互关闭、进入战斗、对象销毁或场景重载时，必须取消未提交拖动且不残留预览或选择效果。

#### 5.2.4 将部署区单位撤回待部署区

玩家选中部署区中的单位后，可以通过该单位选择效果上的撤退按钮发起撤退，将该单位从部署区移回待部署区。

撤退生效前，需要按照待部署区现有的严格堆叠和槽位容量规则检查返回结果：

- 若存在 `type ID`、精英化等级和 Buff 完全一致的堆叠，则单位返回该堆叠，不新增槽位；
- 若不存在可合并堆叠但待部署区仍有空槽位，则单位占用一个新槽位；
- 若单位无法堆叠且待部署区已经达到容量上限，则撤退失败，单位位置、所属区域和玩家资源均保持不变。

撤退成功后：

1. 从部署区移除该单位及其部署坐标；
2. 将单位所属区域改为待部署区，并按严格堆叠规则加入对应堆叠或新槽位；
3. 返还该单位已占用的 `100%` 部署费用。

点击撤退按钮后不进行二次确认；状态层立即执行容量、严格堆叠和费用检查。撤退失败时的具体 UI 表现后续补充。

#### 5.2.5 准备就绪与取消准备

玩家点击“准备就绪”后：

- 禁止继续部署单位；
- 禁止继续交换单位位置；
- 禁止继续移动已部署单位；
- 禁止将已部署单位撤回待部署区；
- 当前阵型保持不变；
- 在战斗阶段正式开始前，玩家可以取消准备并恢复上述操作权限。

已准备期间仍允许打开或关闭自己的商店、购买单位、升级、刷新以及冻结或解除冻结商品。新购买单位仍按商店购买规则进入待部署区或 `Overflow`，但在取消准备前不能部署、移动、交换或撤退单位。

当前本地 UI Demo 中，点击准备不会提前结束准备阶段，准备阶段仍在 `30` 秒倒计时结束后进入战斗。进入战斗阶段时隐藏等级按钮、商店和准备按钮，并强制关闭已经打开的商店。战斗结束返回准备阶段时，准备状态重置为未准备。多人状态同步、取消准备的网络截止时间以及未来“全员准备后提前开始”的规则后续补充。

### 5.3 从准备阶段进入战斗阶段

当前本地 UI Demo 在准备阶段倒计时结束时进入战斗。点击准备只锁定阵型，不提前结束倒计时。未来多人版本是否在所有玩家均已准备后提前结束准备阶段，仍待后续确认。

准备阶段结束后：

1. 禁止玩家继续修改阵型；
2. 从玩家单位集合中永久移除所有处于溢出区的单位；
3. 若本地玩家部署区为空，则从待部署区选择部署费用最高且当前费用足够支付的可部署单位，正常扣除费用并自动部署到一基本地阵型坐标 `(5,2)`；
4. 若部署区为空且不存在可自动部署的单位，则不凭空创建单位，本场战斗由另一方获胜；
5. 保存每名玩家当前的已部署单位及其位置，并生成不可变战斗输入快照；
6. 当前四玩家本地 Demo 固定配对为玩家 1 对玩家 2、玩家 3 对玩家 4；每组第一名玩家为 Home，第二名玩家为 Away；
7. 为两组配对分别生成战斗输入并额外计算第二场独立战斗；不得复用或复制另一组的输入、事件流、胜方或演示状态；
8. 将游戏状态切换为战斗阶段；
9. 开始执行战斗阶段初始化流程。

溢出区属于局内玩家单位维护状态。进入战斗阶段时移除溢出单位是回合状态机必须调用的阶段转换操作，不由 UI、战斗 Core 或演示层隐式执行。

自动部署只在部署区完全为空时发生。多个单位具有相同最高可支付部署费用时的最终选择规则尚未确认；当前固定测试数据应避免出现需要依赖该决胜规则的情况。

### 5.4 战斗阶段

战斗阶段开始后：

1. 系统根据对战配对确定主场方和客场方；
2. 主场方阵型使用本地阵型坐标，客场方阵型旋转到红方半场；
3. 双方单位分别从蓝门和红门一侧进入场地，并向对应阵型位置移动；
4. 等待预定的战斗开始时间；
5. 战斗计算系统按照逻辑帧预先计算完整战斗内容和单场战斗结果；
6. 战斗演示系统根据观察者的主客场视角播放计算结果；
7. 玩家不能直接操作战斗中的单位。

战斗计算使用进入战斗阶段时封存的玩家状态快照。战斗中的当前生命、伤害、死亡和胜负只属于该场战斗，不修改玩家在局内持有的单位、精英化等级、区域、阵型或部署费用。

当前四玩家本地 Demo 同时持有两场独立战斗：

- `MatchAB`：玩家 1 为 Home，玩家 2 为 Away；
- `MatchCD`：玩家 3 为 Home，玩家 4 为 Away。

两场战斗分别由各自双方的封存快照生成并调用确定性战斗 Core；每份输入只计算一次并编译为可按任意演示 Tick 采样的只读表现 Track。两场 Track 共用一个演示时钟和播放速度；未显示的战斗也随该时钟推进。切换观察目标只切换所选战斗及 Home/Away 观察视角，不重新计算战斗，也不从 Tick 0 重新推进事件。切换时精确恢复位置、生命、护盾、死亡和动作类型，但 Spine 动画只从当前动作类型的开头播放，不恢复动画内部进度。较早结束的战斗保持最终状态；全局演示 Tick 到达两场 Track 中最大的结束 Tick 后返回准备阶段。

移动路径、入场顺序、等待时间和异常处理方式后续补充。

当前第一阶段可以从测试对战数据直接初始化战斗，不要求先执行准备阶段。测试输入至少需要包含：

- 参与本场战斗的双方玩家及主客场关系；
- 每个玩家的单位状态快照，包括玩家已拥有的单位实例和该玩家当前商店中的单位候选记录；
- 每条单位记录的独立单位 ID；
- 每条单位记录的 `type ID`；
- 每条单位记录所在的区域，包括待部署区、部署区或商店；
- 已部署单位的本地阵型坐标；
- 每条单位记录当前拥有的 Buff。

只有处于部署区的单位参与本场战斗计算；待部署区和商店中的记录只作为玩家状态快照的一部分保留。

TASK-002 固化的第一阶段 fixture 使用 `battle-fixture-v1`，由 Player-safe 的 `Resources/BattleFixtures` 文本资源承载。它包含 `schemaVersion`、`battleId`、`maxTicks`、Home/Away 双方完整快照、单位类型定义和 Buff 原始占位数据。单位类型当前包含 HP、攻击、防御、法抗、移动速度（厘米/秒）、攻击间隔 Tick、攻击动画时长 Tick、伤害类型、攻击方式、阻挡容量和非负嘲讽等级；攻击时间字段必须以整数 Tick 表示。未知 schema、重复 ID、未知类型、非法区域或坐标、无效数值和不一致的部署坐标必须拒绝加载并返回结构化错误。该格式是可替换的第一阶段测试格式，不代表长期发布格式已经确定。

### 5.5 战斗结算

战斗结束后，系统根据结算规则扣除相关玩家的生命值。

结算完成后：

1. 判断是否有玩家被淘汰；
2. 判断是否已经满足整局游戏的胜利条件；
3. 若对局尚未结束，则进入下一回合的准备阶段；
4. 若只剩一名玩家未被淘汰，则结束本局游戏。

具体扣血公式、平局处理、超时处理和淘汰规则后续补充。

## 7. 战斗系统

战斗机制可参考 [PRTS Wiki：作战机制](https://prts.wiki/w/%E4%BD%9C%E6%88%98%E6%9C%BA%E5%88%B6#%E4%BC%A4%E5%AE%B3%E5%8F%8A%E5%85%B6%E5%A4%84%E7%90%86)。

该页面仅作为设计参考。若外部资料、现有代码和本文档之间存在冲突，应以本文档中已经确认的规则为准；本文档未明确的机制不得直接照搬原作，应先向项目负责人确认。

### 7.1 逻辑帧

战斗计算以离散的逻辑帧推进：

- 逻辑帧是允许单位行动、位置、生命值、Buff、阻挡关系和其他战斗状态发生改变的最小战斗计算步；
- 移动、索敌、阻挡、攻击、伤害、死亡和其他战斗行为只能在逻辑帧中更新；
- 逻辑帧不得依赖 Unity 渲染帧率或 Unity 物理碰撞结果；
- 相同的初始数据和战斗规则必须产生相同的战斗计算结果；
- 战斗演示可以使用更多渲染帧在相邻逻辑帧之间插值，但插值结果不得影响战斗计算。

第一阶段逻辑帧固定为 `20 TPS`，即每 Tick `0.05` 秒。权威计算使用显式 Tick 推进，不读取 Unity 时间、物理或渲染帧率。源秒数无法精确换算为整数 Tick 时向上取整，确保权威间隔与动画时长不短于源秒数。

### 7.2 移动、索敌与阻挡

- 当前版本不存在远程单位，所有单位均按照近战单位规则行动和攻击；
- 正常索敌只考虑敌方存活参战单位，依次按“到自身的欧氏距离平方”“到索敌方自己门格的欧氏距离平方”和稳定升序 unit ID 决胜；Home 门格为 `(5,1)`，Away 门格为 `(5,8)`；
- 单位在逻辑帧中朝当前锁定目标的当前位置进行确定性定点直线移动，单 Tick 不得越过目标；
- 攻击范围与阻挡范围均严格为 `< 0.25` 米。单位向当前目标移动时，不得在单 Tick 内跨越该范围并落到目标中心；移动终点至多推进到首个严格小于 `0.25` 米的可表示位置。该限制不依赖任一方是否仍有阻挡位；
- 目标死亡后不在该 Tick 内立即重选，而在下一 Tick 的索敌阶段重选；
- 单位之间的距离严格小于 `0.25` 米时可建立对称阻挡关系，距离恰好等于边界不建立；每条关系同时占用双方各一个阻挡容量。单位只要仍有空位，可以同时阻挡多个单位；任一方死亡、失效或超出半径时双向解除该关系；
- 阻挡在本 Tick 的批量移动之后评估。任一单位正在向自己的目标移动时，也可被另一名以它为目标、且进入范围的敌方单位拦截；建立关系后双方从下一 Tick 起停止移动，不会改写各自的常规索敌目标。攻击优先保留仍在攻击范围内的常规目标；仅当该目标离开攻击范围或失效时，才改为按稳定升序 unit ID 选择存活阻挡对象。没有阻挡关系的单位同样会在其常规目标进入攻击范围时停止移动并攻击；
- 对同一单位 A 的同 Tick 入站阻挡候选，A 依次选择：`A 当前锁定目标`（如也在候选内）、候选单位嘲讽等级降序、候选单位到 A 自己门格的欧氏距离平方升序、候选 unit ID 升序，直到 A 或候选方的阻挡容量耗尽。不同目标同时争用同一候选的剩余容量时，按目标 unit ID 升序作为最终稳定兜底；
- `unit-source-v1` 源单位 JSON 使用 `tauntLevel` 表示基础嘲讽等级；其值映射到 Core 的同名 `tauntLevel`。当前 `gopro` 与 `arcslma` 均明确配置为 `0`；
- 攻击不要求攻击者与目标之间已经建立阻挡关系，但目标必须位于攻击者的攻击范围内；Attack 事件生成后，其 Damage 结算只要求攻击者和事件中记录的目标仍存活，目标在动画期间离开攻击范围不取消该次伤害；
- 已有任一阻挡关系的单位停止移动；未建立关系的单位在其当前攻击目标仍位于攻击范围内时同样停止移动，不会因目标满容量而继续前进。
- 表现层单位默认面向世界右方；Move 事件只有世界 X 方向的位移会更新左右朝向，向左时相对默认朝向绕 Y 轴旋转 `180°`，向右恢复默认朝向。世界 Z 方向仅表示上下移动，不改变左右朝向；Attack 事件发生时，攻击者按攻击目标的投影世界方向更新左右朝向，纯 Z 方向仍保留现有左右朝向，后续 Move 事件可再次覆盖该朝向。

以下规则后续补充：

- 位移或传送时的阻挡关系清理。

### 7.3 攻击数据

单位每次攻击都会生成一份攻击属性数据，用于描述并处理本次攻击。

攻击数据至少可能包含：

- 攻击力；
- 攻击类型；
- 是否致死；
- 是否属于环境伤害；
- 攻击来源；
- 攻击目标；
- 其他用于伤害、效果和结算的属性。

攻击数据的完整字段、生命周期、修改顺序和结算流程后续补充。

### 7.4 伤害计算

当前版本支持物理伤害、法术伤害和真实伤害：

- **物理伤害**：本次伤害为“攻击力减防御力”与“攻击力的 `5%`”中的较大值，即 `max(攻击力 - 防御力, 攻击力 × 5%)`；
- **法术伤害**：法术抗性按百分比降低伤害，本次伤害为“攻击力乘以 `(1 - 法术抗性 / 100)`”与“攻击力的 `5%`”中的较大值，即 `max(攻击力 × (1 - 法术抗性 / 100), 攻击力 × 5%)`；
- **真实伤害**：不受防御力和法术抗性影响，直接造成本次攻击数据指定的伤害。

第一阶段权威伤害全部使用整数并向下取整：物理为 `max(atk - def, floor(atk * 5 / 100))`，法术为 `max(floor(atk * (100 - res) / 100), floor(atk * 5 / 100))`，真实伤害直接使用攻击指定整数值。正式 fixture 仅使用非负攻击/防御和 `0..100` 法抗；异常属性处理仍待确认。

### 7.4.1 攻击、死亡与 Tick 内结算

- 单位维护下一次允许攻击开始的最早 Tick；首次满足范围且不在冷却时可立即攻击；
- 攻击开始产生 Attack 事件和待结算攻击。其有效动画时长为 `min(原始动画 Tick, 攻击间隔 Tick)`，并在有效动画结束 Tick 结算伤害；
- 攻击者在出伤前死亡时取消待结算攻击；目标在出伤前死亡时取消该次 Damage，但攻击者仍须保持已开始的攻击动画，并在该攻击有效动画结束 Tick（含）前不得移动。两种情况均保留已产生的 Attack 事件；
- 同一 Tick 到达的有效攻击先基于结算阶段开始时的存活快照统一计算和应用伤害，再统一产生 Death；因此该批中将死亡的攻击者仍能完成已到达伤害；
- 死亡单位在下一阶段起不再移动、索敌、阻挡或发起攻击，并双向清理目标、阻挡和待结算关系。

### 7.5 单场战斗结果

- 一方全部参战单位死亡且另一方仍有存活单位时，存活方是本场唯一胜方；
- 单场战斗结果属于战斗计算输出，不得由动画播放、Unity 碰撞或观察者视角决定；
- 主场方和客场方观察的是同一份战斗结果，客场视角只对演示内容进行坐标和方向转换。

双方同时失去全部单位、达到 `maxTicks` 和其他无法唯一判定的情况返回明确的 Unresolved 结果与原因，不伪造胜方。第一阶段输出只读且严格有序的 Spawn、Move、TargetChanged、BlockStarted、BlockEnded、Attack、Damage、Death 和 BattleEnded 事件；每条事件包含 Tick 与 Tick 内递增 sequence。

### 7.6 单位世界空间血量与护盾状态条

单位战斗状态条属于战斗演示对象，不属于屏幕空间 UI。它必须作为世界空间物体附着于 `DefaultUnit`，跟随单位移动，但不得影响权威战斗计算、碰撞、索敌、阻挡或伤害结果。

状态条至少接收以下只读表现数据：

- 当前观察者视角下该单位是否为敌人；
- 血量上限 `maxHitPoints`；
- 当前血量 `currentHitPoints`；
- 当前护盾 `currentShield`；
- 为绑定、切换观察视角和生命周期清理所需的 unit ID、单位阵营/观察者阵营或等价信息。

敌我关系相对于观察者计算：Home 观察者把 Away 单位视为敌人，Away 观察者把 Home 单位视为敌人。切换观察视角时，现存单位的状态条必须立即更新敌我外观，但不能修改单位阵营或战斗结果。

状态条使用现有资源：

- `Assets/Resources/UI/Texture/slider_hp_back.png`：血条背景；
- `Assets/Resources/UI/Texture/slider_hp_enemy.png`：敌方血量；
- `Assets/Resources/UI/Texture/slider_hp_fill.png`：我方血量；
- 护盾使用纯白色表现，可复用合适的填充纹理并着色为白色，不要求新增护盾贴图。

状态条的总长度为 `90` Unity 世界坐标单位，视觉位置位于单位脚下约 `25` Unity 世界坐标单位处。高度可根据背景贴图宽高比和实际观感做最小调整，但不得改变总长度和左右语义。状态条必须保持面向观察者且水平可读，不得随单位左右转向而镜像；血量始终从左侧开始，护盾始终位于右侧。

令总宽度 `W = 90`、血量上限 `M = maxHitPoints`、显示用当前血量 `H = clamp(currentHitPoints, 0, M)`、显示用当前护盾 `S = max(currentShield, 0)`、总容量 `C = M + S`。必须先计算血量上限宽度，再在该宽度内计算当前血量宽度：

- 血量上限宽度 `MaxHpWidth = W × M / C`；
- 当前血量宽度 `CurrentHpWidth = MaxHpWidth × H / M`，从血量上限宽度的左边缘开始填充；实现和调试输出应保留这一两步语义，不得把血量上限宽度省略为不可观察的隐含假设；
- 护盾宽度 `ShieldWidth = W × S / C`，位于总状态条的最右侧；
- 当 `S = 0` 时，`C = M`、`MaxHpWidth = W`；仅当 `H < M` 时显示状态条，满血时隐藏整个状态条；
- 当 `S > 0` 时，无论是否满血都显示状态条；当前血量末端与右侧护盾起点之间未填充的血量上限区域表示已损失血量；
- `M <= 0` 属于非法表现输入，应隐藏状态条并产生可诊断错误，不得除零或反向修改 Core；
- 当前阶段的权威战斗尚不产生护盾，战斗回放中的 `currentShield` 默认为 `0`。TASK-007 只建立护盾显示输入与布局，不定义护盾生成、伤害吸收、消耗、叠加或失效规则。

当单位 GameObject 被隐藏、销毁或回放清理时，状态条随单位一起隐藏或清理。本节不额外定义死亡动画期间血条保留多久；在单位对象仍可见期间，`0` 血量且无护盾按上述规则显示空背景，随后跟随既有死亡/隐藏生命周期结束。

状态条和单位整体必须显示在战场地图之上，不得被地面遮挡。当前项目使用 Built-in Render Pipeline；实现应优先采用仅作用于单位/状态条的世界位置偏移、Renderer 排序、渲染队列或专用透明材质深度设置，不应为此修改全局渲染管线。若 Renderer 排序不能跨越不透明地图的深度遮挡，可以为状态条使用局部的 `ZWrite Off`/合适 `ZTest` 等价方案，但不得让状态条反向参与物理或战斗计算。

### 7.7 战斗表现 Track

权威 `BattleRunResult` 必须保留完整事件序列。战斗演示在 Core 完成后，将事件一次性编译为每场战斗一份只读 `BattlePresentationTrack`，其中每个单位具有独立的单位表现 Track。单位 Track 至少可以按任意演示 Tick 采样：

- 是否已经 Spawn、是否存活和是否显示；
- 逻辑位置与朝向；
- `Idle`、`Move`、`Attack` 或 `Death` 动作类型；
- 实例级 MaxHP、CurrentHP 和 CurrentShield。

动作优先级为 `Death > Attack > Move > Idle`。Damage 只更新 CurrentHP，不产生 Hit 动作，也不打断 Attack；新 Track 播放路径不得调用 Hit 动画。切换观察目标时只恢复动作类型，动画从该动作开头播放。

Core 当前逐 Tick 输出的连续 Move 事件只在表现 Track 中压缩，原始事件不得删除。压缩后的 Position Segment 按时间线性插值，并且在每个原始 Move Tick 的位置误差不得超过 `1 Unity 世界坐标单位 = 1 cm`。Spawn、Attack、BlockStarted、BlockEnded、Death、BattleEnded、移动开始、移动停止和最终位置必须是误差为 `0` 的精确关键帧；不得跨越没有 Move 的 Tick 压缩。

Track 编译器必须支持战斗中临时生成单位。每个合法 Spawn 都可以在任意 Tick 建立新的单位 Track，不能要求单位必须存在于初始 `BattleInput`。动态单位：

- 必须引用目录中已有的 Type ID，用于 Prefab、SkeletonData、`unitSkeletonType` 和动画名称映射；
- 使用与 Spawn 绑定的实例级属性，包括 MaxHP、CurrentHP、CurrentShield 及实际战斗属性，不得由目录基础值覆盖；
- 在单场战斗内使用从 `-1` 开始确定性递减的负整数字符串 Unit ID；
- 以 `(BattleId, UnitId)` 作为完整身份，下一场战斗可以重新从 `-1` 开始；
- 不进入跨回合玩家状态。

初始单位的实例级属性可以来自已封存的不可变 `BattleInput`、`BattleRunResult` 附带的实例快照或扩展后的 Spawn 载荷；不在初始输入中的动态单位必须由 Spawn 载荷或与其绑定的等价不可变实例快照提供完整实例属性。初始玩家单位不得使用可解析为负整数的 Unit ID。事件在 Spawn 前引用单位、单场内重复 Unit ID、未知 Type ID、无法从封存输入或动态 Spawn 快照取得实例属性、位置压缩误差超限或 Track 终态与 Core 终态不一致时，必须返回包含 Battle ID、Unit ID、Tick 和 Sequence 的结构化诊断，不得静默跳过该战斗。

## 8. 规则优先级与不确定性处理

规则解释优先级如下：

1. 项目负责人在当前任务中的明确说明；
2. 本文档中已经确认的规则；
3. `docs/decisions/` 中已接受的设计决策；
4. 当前实现和现有测试所体现的行为；
5. 外部参考资料。

当出现以下情况时，应暂停相关实现并向项目负责人确认：

- 玩家可见行为不明确；
- 数值、费用或结算方式不明确；
- 回合状态转换不明确；
- 多人同步的权威端和冲突处理方式不明确；
- 胜负、淘汰或异常情况的处理方式不明确；
- 本文档、现有代码、测试或外部资料互相冲突。

对于不影响游戏规则和玩家可见行为的低风险实现细节，可以采用最小、可逆且符合现有代码风格的方案，但必须在任务汇报中说明所作假设。

## 15. `SUMMON_JELLY_MINIONS` 果冻召唤（2026-07-26）

- 自动技能的 SP 回复速率是全局规则：20 TPS 下每秒回复 `2 SP`，即每 `10 Tick` 回复 `1 SP`。每个单位的每个技能仍保存彼此独立的私有 SP 与施放次数；该速率不写入单位或能力源 JSON。`SUMMON_JELLY_MINIONS` 初始为 `5 SP`、需要并消耗 `15 SP`，因此持续存活且战斗未结束时首次在 Tick `100` 施放，消耗后再次积累并在 Tick `250` 施放。
- 每次施放以施法者当前位置为中心，在一个地图格大小的正方形内生成三个 `5504`。该正方形边长固定为 `1 m`（`100 cm`），位置由 Core 的整数定点算法确定，不使用 Unity 浮点随机或 `Random`。
- 新生成单位不继承施法者的路径、目标或阻挡关系。它们在生成 Tick 只产生 Spawn 与不可变实例快照，从下一 Tick 起才按普通单位的索敌、嘲讽与稳定决胜规则各自重新选择目标和行动。
- 同一 Tick 先完成已到达伤害、Death、阻挡解除与索敌清理，再判断战斗是否终局。若清理后已终局，该 Tick 不回复 SP、不施放定时技能，召唤不能延长已经结束的战斗；BattleEnded 仍是该终局 Tick 的最后事件。
- `BattleRunResult` 为动态实例保留唯一负数实例 ID、生成位置、激活 Tick、完整单位状态及只读实例快照索引。Presentation 只能从该封存结果编译动态 Track：初始单位在 Tick `0` 建立视图，动态 `5504` 在各自 Spawn Tick 建立视图；Home/Away 投影、暂停、变速、观察切换和 Replay 均不得重算或回写 Core。Replay 清理旧动态视图，并在再次越过对应 Spawn Tick 时用相同 ID 与快照重建。
- `Assets/GameData/Units/Json` 与 `Assets/GameData/Abilities/Json` 是人工维护的权威源；单位/能力目录生成器只读、校验、稳定排序并写各自生成目录，不回写源 JSON。任何已部署单位引用的 innate ability 都必须在封存的 ability definitions 中解析成功；未知能力 ID 或未知召唤类型返回结构化验证错误，不允许静默省略能力。
